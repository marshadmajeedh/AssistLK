# AssistLK External Agent Service Contract

**Status:** Authoritative Communication Specification  
**Applies To:** Out-of-process Python agent services (`agent-services/`) & .NET Agent Client Adapters (`AssistLK.Application`)  
**Related Documents:** [External Python Agent Service](external-python-agent-service.md), [Component Boundaries](component-boundaries.md)

---

## 1. Architectural Philosophy

When a teammate builds an agent using Python (e.g., FastAPI, LangChain, LangGraph), the agent operates out-of-process as a **pure inference and reasoning worker**. 

### Authority & Responsibility Matrix

| Area | .NET 8 Backend (`AssistLK.Api` / `AssistLK.Application`) | Python Agent Service (`agent-services/<name>/`) |
|---|---|---|
| **Authentication & Authorization** | **Authoritative:** Validates JWT, verifies customer ownership, enforces RBAC. | **Prohibited:** Never inspects or issues JWT tokens. |
| **Workflow State Machine** | **Authoritative:** Transitions `Created` → `Analyzing` → `ReadyForMatching`, etc. | **Prohibited:** Has no concept of persistent workflow transitions. |
| **Data Persistence** | **Authoritative:** Sole accessor of PostgreSQL via EF Core repositories. | **Prohibited:** Direct database connection strings are forbidden. |
| **Domain Entities** | **Authoritative:** Instantiates and mutates domain models. | **Prohibited:** Operates solely on provider-neutral JSON payloads. |
| **Audit & Memory** | **Authoritative:** Records execution metrics, safety audits, and semantic memory. | **Stateless / Request-scoped:** Returns clean structured output. |
| **AI Reasoning & ML** | Delegates to agent via HTTP/gRPC. | **Authoritative:** Executes prompt pipelines, embeddings, ranking, and validation. |

## 2. Standard Wire Protocol & JSON Schema

All communications between .NET and Python agent services must adhere to this provider-neutral contract over internal HTTP/JSON (or gRPC).

### 2.1 Agent Request Specification

```json
{
  "$schema": "http://json-schema.org/draft-07/schema#",
  "title": "AgentRequest",
  "type": "object",
  "required": ["requestId", "agentName", "operation", "timestamp", "input"],
  "properties": {
    "requestId": {
      "type": "string",
      "format": "uuid",
      "description": "Unique correlation ID generated by .NET for tracing across services."
    },
    "agentName": {
      "type": "string",
      "description": "Canonical identifier of the target agent (e.g. 'ProviderMatchingAgent')."
    },
    "operation": {
      "type": "string",
      "description": "Specific action requested (e.g. 'match-providers', 'coordinate-schedule')."
    },
    "timestamp": {
      "type": "string",
      "format": "date-time",
      "description": "UTC timestamp of request dispatch."
    },
    "parameters": {
      "type": "object",
      "description": "Optional execution parameters such as maxCandidates or threshold."
    },
    "input": {
      "type": "object",
      "description": "Domain-specific input payload tailored strictly for this operation."
    }
  },
  "additionalProperties": false
}
```

      "type": "object",

## 3. Strict Data Boundary & Privacy Invariants

To guarantee system security and client privacy, the following information **MUST NEVER** be passed across the wire:

- ❌ **No Internal Chain-of-Thought:** Raw intermediate reasoning chains, internal prompt scratchpads, and sensitive model instructions must not be exposed in public API responses.
- ❌ **No Database Credentials or Connection Strings:** Python microservices must have no knowledge of database hosts, ports, passwords, or schemas.
- ❌ **No JWT Tokens or Cryptographic Keys:** Bearer tokens, signing keys, and hashing salts are handled exclusively inside `AssistLK.Api`.
- ❌ **No Unnecessary Customer PII:** Only data strictly required for the specific reasoning task (e.g., problem description, approximate coordinates) should be passed. Customer emails, phone numbers, and payment details must remain masked.

## 4. Resilience & Error Handling Policies

### 4.1 Timeout Handling
- **Default Timeout:** 10 seconds for standard reasoning requests.
- If the Python agent does not respond within the timeout window, the .NET client adapter must cancel the `CancellationToken` and treat the invocation as a transient timeout.

### 4.2 Unavailable Service Behavior
- If the Python agent service is offline (e.g., HTTP 503, connection refused), the .NET workflow must:
  1. Record an execution metric in `AgentExecutionMetrics` indicating service unavailability.
  2. Transition workflow state to safe fallback mode or alert the administrator.
  3. Never crash the host ASP.NET Core process.

### 4.3 Retry Policy Principles
- **Idempotency:** All agent operations must be designed to be idempotent for a given `requestId`.
- **Transient Failures Only:** Retries are permitted only for network connection failures or HTTP 503 / 504 responses.
- **Maximum Retries:** Maximum 2 retries using exponential backoff with jitter (e.g., 500ms, 1500ms).
- **No Retry on Bad Requests:** HTTP 400 or schema validation failures must not be retried.

### 4.4 Structured Validation & Safe Fallback
- The .NET client adapter must strictly validate the deserialized JSON response. If properties are missing or values fall outside permitted ranges (e.g., `confidence < 0` or `confidence > 1`), the payload is rejected.
- When an agent fails or produces invalid output, the application falls back to safe defaults (e.g., queuing for human review or assigning an `Unknown` classification requiring manual triage).
